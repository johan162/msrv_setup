Introduction

With the almost ubiquitous presence of mobile devices it becomes crucial to be able to access mail from any device anywhere and still read and manipulate the same mails regardless of which device is used. The easiest way to achieve this with close to zero setup effort is to use a public mail provider, for example GMail, Hotmail etc.

However for users that require more fine grained control over message handling a public mail provider might not be a viable option. Reasons that might require such a setup includes but are not limited to:

  • need for automatic processing of messages with external programs at message arrival (such as automatic replies depending on message content or perform other pre-defined actions such as scannig messages for viruses)

  • control over mail backup

  • collection of mails from several accounts into one master repository

  • unable to comply with the license of the public mail provider

  • need for an ad-free mail client

  • needs mail to be sent from a specific domain

  • privacy concerns

The rest of this tutorial will be spent going through, in details, how to make such a setup based on a OpenSuSE Linux/GNU distribution.

Why another mail tutorial?

There is no shortage of various notes and tutorials trying to show how to do a server setup like this. Our experience is however that many of them, while working (in some respect), have one or more misunderstandings or present obsoleted knowledge based on old ways of doing things. In many cases recommendations are handed down from older tutorial and seen as truth - because they work - but are incomplete or in worst case have been deprecated since long.

This tutorial, while substantially longer, aims at describing a correct and modern setup as well as how it works and how the components interact. Many misunderstanding stem from a poor grasp of the overall picture on how these component fits together. It is our belief that in order to configure a working setup one must understand what one is doing. Just taking random bits of code from "the net" might give, by sheer luck, a working setup but it might as likely have created an open relay for spammers to use (which is very bad).

Especially the SSL/TLS setup using openssl will be covered and explained in more details than usual in descriptions like this since much information available on "the net" is just plain wrong or at best shows very, very, antiquated ways of configuring a SSL/TLS setup.

Goals with this tutorial

The setup we will describe in this tutorial will allow any device capable of IMAP message handling (all modern devices do) to connect and synchronize mails from a central repository meaning that any change from any device will be visible to all other devices. The setup will also allow clients to send mails through this server (acting as an SMTPD server).

The setup assumes a "home server" which is not directly connected to the internet and configured as an official mail server for some domain. This also implies the need to relay mails to be sent through a “real” mail server (most likely an ISPs server) that is properly connected to the internet. An overview of the principle of our setup and all constituting parts are shown in Figure 2, “Mail server overview”.

The goal of this tutorial is therefore to describe, in a very detailed way, how to setup an OpenSuSE server to both act as an IMAP and SMTP server. In addition it will use encrypted communication using a SSL/TLS setup based on the openssl library. This will allow secure mail access from any device (e.g. SmartPhones, Ipads, laptops etc.) using either the device's built-in mail client or optionally connected to our web based mail client.

Applicable OpenSuSE versions and pre-requisites

Much of the information here is generic and not specific to OpenSuSE. However, location and structure of specific configuration files are distribution dependent. This document has been verified on OpenSuSE 11.4 as well as 12.1. Most ofthe details given in this tutorial should also be valid on older 11.x OpenSuSE releases. OpenSuSE resembles the RedHat distribution in some respect but has enough differences of its own to not make it directly compatible. Other systems (for example Ubuntu) uses a rather different setup structure so while the principles still apply the details will not match.

One main difference noticeable between 11.4 and 12.1 is that in 12.1 the older SySV init file handling has been replaced with the more modern systemd init file handling. This has several advantages such as parallelizing startup scripts (hence reducing boot time). Fortunately there is a compatibility layer so that old /etc/init.d/ startup scripts will work as usual and redirect the start/stop commands to systemd (see systemd – boot faster and cleaner)

Installed components

We will assume that all the components listed below are installed on the server. They are all available (with one exception as noted below) from the standard OpenSuSE repository as packages. For now it is enought if these components are installed but not configures - this is what the rest of this tutorial is all about. All these components can be installed from the Yast2 package manager as listed below (the "core packages" indicates the minimum needed packages.)

  • Apache v2.x - HTTP server (will be referred to as only Apache in the rest of the document).

    Core packages: apache2, apache2-prefork, apache2-utils, libapr-util1, libapr1

  • PHP5 - With at least the modules php5-curl, php5-openssl and php5-sockets installed

    Core packages: apache2-mod_php5, php5-mysql,php5-curl, php5-openssl, php5-sockets

  • Postfix - Mail daemon used to receive and send mails.

    Note: The default mail daemon (MTA) in OpenSuSE 12.1 has changed to exim if a full KDE/X-Windows installation is done. This means installing postfix might trigger a warning that it conflicts with exim and that it will be un-installed. Just answer yes in that case. In case you install the default text server postfix will already have been installed.

    Core packages: postfix

  • Fetchmail - Used to fetch messages from other mail accounts

    Core packages: fetchmail

  • Dovecot v2.x - IMAP server that allows access to your stored mails.

    Note: Makes sure that Dovecot 2.x is installed and not Dovecot 1.x. OpenSuSE by default installs the older version 1.x of Dovecot. Dovecot 2.x is available in the OpenSuSE repositories (as dovecot2). We will simple refer to this as Dovecot.

    Core packages: dovecot20

  • MySQL - Database server (needed for the Roundcube webmailer)

    Core packages: mysql-community-server, mysql-community-server-client

  • Procmail - Used for rule based mail filtering which will allow things like sorting mails into folders depending on there content or do other types of automatic processing based on the content of the messages.

    Core packages: procmail

  • Spamassassin - Tool to help identify junk mails (spam)

    Core packages: spamassassin, perl-Mail-Spamassassin

  • openssl - Tool to handle encryption and creation of certificates (this package is installed by default in the Minimal Server Selection)

    Core packages: openssl

Caution

Please make absolutely sure that all of the above components are installed before proceeding!

All necessary component can be installed by running the following command as root

$> zypper in apache2 apache2-prefork apache2-mod_php5 php5-curl \
php5-openssl php5-sockets postfix fetchmail dovecot20 procmail \
mysql-community-server mysql-community-server-client \
spamassassin perl-Mail-Spamassassin

There is also one final package that strictly speaking is not necessary but that we strongly recommend. This is to install a Web-based mail client. Having a web-based mail setup has the advantage that it will allow safe and secure access (using https://) to mails from any networked computer in the world. In this tutorial we will use "Roundcube" (http://roundcube.net/).

The application style of the modern (and AJAX based) Roundcube also makes it a compelling alternative even to native mail clients such as KMail. Roundcube is not as of this writing available as a package for OpenSuSE. However as a Web-applications it is straightforward to install and set it up using the included installer.

What level of experience is needed and how long will it take?

A certain maturity with Linux is assumed but mostly the ability (and willingness) to lookout for details is what matters. As in a mathematical proof every single detail counts. There are literally hundreds of pages in the manuals for all the components we touch upon here so the details described here are only the details that really matters - the need to know details.

Setting up a complete IMAP/SMTP server correctly the first time requires an eye for details. Even experienced administrators will make mistakes. The main advantage with experience is that debugging various issues gets faster since likely problem spots are known by experience.

The setup of a working server will likely take several hours rather than minutes. So patience is needed as well as careful reading with a willingness to go back and double check everything at least three times!

Tip

We strongly encourage to install the server in a virtual machine installation (for example using VirtualBox) since that will easily allow going back to a known pristine state in case of "unrecoverable error". Compare this with having to re-install a physical server since one is not sure after a while which of all the settings that were changed was wrong.

Once a working server in a virtual machine is established it is also easy to move the virtual server, for example to a new server when the hardware is upgraded. This allows an easy upgrade path to future OpenSuSE version as well without having to reconfigure a complete mail server at each upgrade. When in the future OpenSuSE v13.1, v14.1, etc. comes out there is nothing that prevents running a virtual mail server based on 11.4 or 12.1. The core protocols of the internet are not very likely to have changed dramatically even by then so the virtual server will still be valid.

OpenSuSE has pre-built packages for VirtualBox which makes it straight forward to install.

The only minimal drawback with a virtual server is the need to reserver some RAM memory. However, given that it is perfectly fine to run a complete mail setup on 512MB (or less) this should be considered a small price to pay for the flexibility it will give.

About this document

This tutorial was written in plain text format (UTF-8 encoding) using the DocBook XML markup. To render the styled output from the XML sources the DocBook 1.76.1 XSL stylesheets was used together with the xsltproc XSLT processor

To produce the PDF output the DocBook XML were first transformed into an FO format which was then rendered with the Apache FOP processor into the final PDF format. In order to get the current look and feel of the document a customized XSL stylesheet was used. To style the HTML output both a custom HTML XSL stylesheet and a CSS stylesheet was used.

As source editor oXygen XML editor was used and the transform process into HTML and PDF was controlled by a Phing script.

References for technologies used to produce this document

  • DocBook, is a defined XML schema that identifies the meaning of different parts of a document. It is specifically well suited to write technical computer related documents but can also be used to write generic documents. By itself DocBook does not care about how the document is displayed (in contrast to for example OpenOffice or Word).

    In order to transform the DocBook XML document into something suitable for human reading (such as HTML and PDF) a set of XSL stylesheets are used. They are known as the DocBook XSL stylesheets. The current version as of this writing was 1.76.1

  • XSL, stands for [Definition: Extensible Stylesheet Language Family] is an overall term for three technologies used to process XML documents into other XML documents. The included technologies are:

    • XSLT, is a programming language for transforming XML documents into other well formed XML document, for example (X)HTML documents.

    • XPath, a way to uniquely identify different parts of a well formed XML document. This is used as the search language in the stylesheet to specify what elements to transform.

    • XSL-FO, is a defined XML schema that defines how a printed output should be displayed. This format can later be easily transformed into other formats suitable for printed output such as PDF or RTF.

  • xsltproc, is the GNOME projects XSLT processor that uses an XSL(T) program to transform one XML document into another. This is one of the few XSLT processors written in C (most others are written in Java)

  • fop, is the Apache projects XSL-FO processor. This is primarily used to transform a XSL-FO document into a PDF document.

  • Oxygen, the XML editor used to for writing the source XML document.
