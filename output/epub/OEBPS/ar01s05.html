5 Setting up Dovecot

The reason to start with Dovecot rather than Postfix is twofold. One is that postfix will make use of the Dovecot SSL/TLS certificates (as shown in Figure 9) and the second is that postfix will use Dovecot SASL service to authenticate incoming SMTP requests. SASL stands for Simple Authentication and Security Layer and is a standardized protocol to handle authentication. The reason for this is that we want incoming SMTP traffic to be authenticated forcing users to log in before being able to send mails through our SMTP(s) server. Since postfix does not provide any authentication service by itself it must make use of some service provided by another component, Dovecot in this case.

The reason for re-using the SSL/TLS certificates from Dovecot in postfix is partly laziness; Dovecot comes with a small script that makes the creation of certificates very easy.

Tip

We also remind of the more complete description on how to use openssl directly in . to create a certificate hierarchy with a bit more control that comes from better understanding. But for now we make use of the utility script that comes with Doevcot2 since it is the easier way for a newcomer to do what needs to be done.

In the following we assume that you have installed Dovecot2 through Yast. Before continue please make sure that Dovecot 2.0.x is installed and not 1.x. For some reason SuSE still uses 1.x as the default version of Dovecot (instead of Dovecot2).

Note

The script that comes with Dovecot does roughly the same step as the previously used gensslcert (for Apache2) but stores the resulting certificate files in a different directory and also uses the *.pem endings instead of *.crt/*.key (see the section on SSL/TLS certificates for an explanation of *.pem vs. *.crt/*.key suffixes)

5.1 Modifying dovecot configuration files

After installing Dovecot all configuration files can be found under /etc/dovecot/conf.d

The files that need editing are listed in Table 5 together with a short explanation of the purpose of each file.

Table 5: Dovecot configuration files that needs modifying

Configuration file Comment

10-master.conf

Enabling and disabling what protocols Dovecot should listen for

10-auth.conf

What methods to use for user authentication

10-mail.conf

Location for mail repositories

10-ssl.conf

Settings for encrypted communication

10-logging.conf

Settings for logging from Dovecot. Useful when debugging issues.

Strictly speaking there is no need to change the last file controlling the logging levels but while setting up the server it is very handy to enable as much logging as possible in order to ease any troubleshooting that may be needed if things don't quite work out as we think.

5.1.1 10-master.conf

Here we need to enable only IMAPS. Make sure that the section service IMAP-login has the following settings:

service imap-login {    
  inet_listener imaps {        
    port = 993        
    SSL = yes
  }
}

Further down in 10-master.conf the configuration for the authentication socket can be found. This will later be used by postfix to check any incoming logins. By default only root is allowed to read on this socket so as long as postfix is run with root privileges the default permissions are fine. However normally postfix is run as a separate user for safety so these permission needs to be relaxed as shown below.

service auth {
  unix_listener /var/spool/postfix/private/auth {
    mode = 0660
    user = postfix        
    group = postfix  
  }
}

5.1.2 10-auth.conf

In this file we must allow plaintext login. This is safe since we are running over a secure SSL encrypted link.

Find the following settings and adjust them as shown

disable_plaintext = no
auth_mechanisms = plain

The above settings will allow a plain text username/password type of login to dovecot.

Note

Some HowTo:s seem to indicate the use of LOGIN as the authentication mechanism for SASL. However, LOGIN is a deprecated mechanism and PLAIN is the recommended way as described in RFC 2595.

For the actual check of username/password Dovecot will make use of the PAM system on Linux which in turn will check any username/password against the Linux standard system users and password files (e.g. /etc/passwd or the shadow version of the password file)

5.1.3 10-mail.conf

The primary purpose of this file is to tell dovecot where in the file system mails are stored. The choice here is system dependent and up to the administrator. In the examples shown below mails are stored in /srv/mail/%u where %u is replaced by dovecot for the name of the user.

As for mail format we strongly recommend to use the maildir format where each mail is stored in its own file. To instruct dovecot to use this format we specify the mail location with a prefix of maildir as shown next. Now find and adjust the following setting

mail_location = maildir:/srv/mail/%u

We must also create this directory. Assuming we have a user called tstuser belonging to the user group users we can now create this mail directory with the proper ownership with the following commands:

$> sudo mkdir –p /srv/mail/tstuser
$> sudo chown tstuser:users /srv/mail/tstuser
$> sudo chmod 700 /srv/mail/tstuser

The above lines will create a mail directory only accessible by root and the specified user. The above steps are needed once for each mail user. In the above we have, somewhat arbitrary, chosen to store each users mail under the /srv/mail directory.

Tip

Another common setup is to store all the mails inside each users home directory, for example in ~/Maildir

5.1.4 10-ssl.conf

Here we need to tell dovecot to enable the basic SSL capability. To do this the first line simply needs to change to

ssl = yes

5.1.5 10-logging.conf

The final step is to enable a more verbose logging. Strictly speaking this is not necessary but during the setup this is extremly handy in order to pinpoint any potential problems until we have a system that is fully working. Find the following settings and adjust them as shown.

log_path = /var/log/dovecot.err
info_log_path = /var/log/dovecot.info
debug_log_path = /var/log/dovecot.debug
auth_verbose = yes
auth_verbose_passwords =plain
auth_debug_passwords = yes
mail_debug = yes
verbose_ssl = yes

Tip

There is yet another level of logging that can be enabled to give details on every single IMAP command received from a client. This is very verbose and should only be enabled during specific troubleshooting sessions. Using this level of debugging requires some basic knowledge of the IMAP protocol in order to make sense of the information. This level of debugging is very useful if one suspects that a mail client sends the wrong IMAP commands (which is not completely unheard of)

This is described in the “Rawlog” section in the documentation of Dovecot (See http://wiki2.dovecot.org/Debugging/Rawlog)

Later on when things are working correctly these settings should be changed since it will generate quite a lot of “noise” in the log files.

5.2 Creating dovecot SSL/TLS certificates

In order to use IMAPS we must first create SSL certificates and keys in much the same way as we did for the Apache. In fact, it would be perfectly possible to reuse the exact same keys and certificates that we created for the web-server. Just watch out for the names of the certificate files.

However as we discussed previously we will use a separate set of certificates for Dovecot and postfix. For the purpose of creating certificates Dovecot includes a small shell script that will call all the necessary openssl commands in much the same way as gensslcert did for the web-server. This utility script is called mkcert.sh and is found in the directory /usr/share/doc/packages/dovecot. To get correct default values in the certificate first open and edit the file dovecot-openssl.cnf (that is in the same directory). This configuration file contains the values used for names and organization in the certificate. Open the file in an editor and change the setting to match the wanted setup.

Before mkcert.sh is run it is also a good idea to edit a line at the end of that file so that the generated certificate is valid for longer than a year which (unfortunately) is hard code in the end of the script. Change the argument “–days 365” in the end of the script to something a bit longer, for example 3650 days ≈ 10 years.

The files generated by this script are shown in Table 6

Table 6: Certificate keys generated for Dovecot

Certificate fileDescription
/etc/ssl/certs/dovecot.pemSSL/TLS certificate. This certificate contains the public key for Dovecot.
/etc/ssl/private/dovecot.pemSSL/TLS private key for the server. Must be kept private at all times!

As you can see this script will not generate any CA (root certificate). In fact the (test) certificate generated by the Dovecot utility script is by definition a root certificate in itself since it is signed by itself. This differs in behavior from the previously used gensslcert script when we configured Apache which created a separate root certificate. The configuration files in dovecot that specifies already have full path names as default so there is no need to change anything else.

Now it is time to restart Dovecot, for example by giving the command

$> rcdovecot restart

If you get an error saying something like

Fatal: execv(/usr/bin/doveconf) failed: Permission denied

Then our friend Novell AppArmour (which is included by default in a graphical OpenSuSE setup) has kicked in and stopped the process from starting. Since it brings too far to also configure AppArmour in this tutorial simple turn AppArmour off for now by opening Yast and go into Novell AppArmour control panel and disable it. For a personal server AppArmour usually creates more problem than it solves. By default it will block many useful services unless those services have been configured to be allowed.

5.3 Testing the dovecot configuration

To verify that the basics of our IMAP server works we can try to manually connect on port 993, however since that requires a setup of a SSL encrypted connection we cannot directly connect to the port (we need to use openssl s_client). So as an alternative we can (as a test) enable normal IMAP in 10-master.conf. Do this by un-commenting the line #port = 143 in the IMAP section at the top of the file. Now restart Dovecot in the same way as before.

We can then login to dovecot using a basic telnet connection

$> telnet localhost 143
Trying ::1…
Connected to localhost.Escape character is ‘^]’.* 
* OK [CAPABILITY MIAP4rev1 LITERAL+ SASL-IR LOGIN-REFERRALS \
ID ENABLE IDLE STARTTLS AUTH=PLAIN] 
Dovecot ready.

The last line indicates that Dovecot is running and has accepted our connection. In order to do anything else we must login using a user in the system.

The IMAP login command is login <user> <password> So if you continue the previous telnet session by logging in using a known user and password (this user must exist in your system and should have a proper mailbox under /srv/mail/) you should now get a reply resembling

10 login tstuser tstpassword
10 OK [CAPABILITY ….] Logged in

If you wonder about the "10" in the beginning of the command this is just an arbitrary tag for the command. All IMAP commands has to be preceded by a user defined tag. When the IMAP server gives back a reply it will always use the tag for the command that caused this output. Tags allows us to know from which command an output comes from. It is possible to give several commands in a row and some might take long time so there is no guarantee that the servers reply will be in the same order as the given commands. Dovecot ignores the actual characters in the tag so it can be completely arbitrary.

The next step is to try list all available folders for this user

10 list “” *
* LIST (\HasNoChildren) “.” INBOX”
10 OK List completed.

The above command also makes sure that dovecot can access the folder (in our case /srv/mail/tstuser)

If you get this far chances are high that the dovecot setup is correct. After we have configured postfix and we have some mails in our inbox we will manually retrieve them as well.

Finally disconnect from dovecot by logging out

10 logout
BYE Logging out.
10 OK Logout completed.

The final step remaining is to have Dovecot start automatically each time the server is started. If you haven't already done so give the command (as root): 

$> chkconfig –add dovecot2

5.4 Verifying the encrypted IMAP connection

For this we need to use the command line tools from the openssl project which should already be installed. To connect to the server using SSL enter the command: 

$> openssl s_client -connect localhost:993

Thiis behaves in principle as a telnet connection with the only difference that the connection is encrypted. After the command is execurted information is printed to the screen about the encryption and the certificates and at the end the words “Dovecot ready.” should be visible. Now the same login test as for the non-encrypted connection can be run and then the list of available folders for the tstuser.

5.5 Troubleshooting Dovecot

More hints on how to debug a non-working Dovecot authentication process is described in the Dovecot troubleshooting documentation at:

http://wiki2.dovecot.org/Debugging/Authentication

If there is problem with mail synchronization after a successful login to Dovecot server there is one other level of logging (apart from the normal logging that can be setup) that can be helpful and that is to have the actual raw IMAP commands to be shown. This can be used when bug reports needs to be filed to non-compliant clients. To enable this one must activate the so called rawlog logging in Dovecot. How this can be enabled is described in detail in the Dovecot documentation at

http://wiki2.dovecot.org/Debugging/Rawlog

5.6 Adding a full text index

In order to drastically (~x1000) speed up full text searches (fts) of mailboxes it is possible to have Dovecot maintain a full text index for each mail folder. The easiest way to do this is to use Dovecots own full text search engine “SQUAT” (“Search Query Answer Tool”).

To add this capability we tell Dovecot to load this plugin by adding the line

mail_plugins = $mail_plugins fts fts_squat

in the file “20-imap.conf”. We must also globally enable these plugins and give some parameters in the file “90-plugin.conf”

plugin { 
  fts = squat 
  fts_squat = partial=4 full=8
}

The index is initially created the very first time a search is performed on a directory so the first time will take extra time and memory depending on the number of mails in the directory. After the first time Dovecot will update the index incrementally as changes are made to the mail directories.

The only drawback enabling indexes is that they will use extra disk space. The needed space depends on the specific settings (see the Dovecot manual). But a minimum index size of ~30% of the total mail size in each directory can be expected. With the parameters as above one can expect ~60% index size. The parameters adjusts the tradeoff between speed of search and space usage.
