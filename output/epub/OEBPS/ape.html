Appendix E - Create SSL/TLS keys and certificates with openssl

In the following we will create our own CA (Certification agency) that will sign all our public keys. This means that to avoid the warnings in browsers about untrusted certificate the CA certificate (our root certificate) should be imported into the browsers. As an example we will show how this is done for the Chrome browser at the end of this appendix.

The main purpose of this section is to show how the bare bones “openssl” command can be used to create certificates rather than relying on the simple but somewhat magical utility scripts we used in the main discussion. We recommend that one you have gotten over the initial chock of dealing with certificates this is actually a simpler method.

As convention we will use the extension *.pem for all keys (since this is the format they keys are in). To distinguish between the public (the certificate) and private key we will add “_public” and “_private” to the main name of the key-pair.

Some documentation uses the suffix “*.crt” and “*.key” for the public and private key in PEM format. However, our opinion is that the suffix should reflect the format of the file (in this case the PEM) format and the use of crt and key as suffixes make things unnecessary complicated. Especially since one might believe that “*.crt” and “*.key” are in themselves are new formats.

At the end of this walk-though we will have to generate the following key-pairs to use in our setup

CA_public.pem, CA_private.pem

This is our own “Root” certificate. This public key is implicitly trusted, i.e. it is trusted because we say so. No higher authority (but us) has sanctioned this key pair.

https_public.pem, https_private.pem

This is the keypair we will use with Apache when https connections are made

mail_public.pem, mail_private.pem

This is the keypair that will be used for both Dovecot2 as well as postfix to encrypt both IMAP and SMTP protocols into IMAPS and SMTPS

Optionally we might also have

https_alt_public.pem, https_alt_private.pem

This is a keypair which makes it possible to access the server under several aliases. This if further described in section E.5

In the process of generating these targets there will also be some intermediate files that strictly speaking is not necessary to keep (but might come in handy later on as we shall see).

The process is now as follows

  1. Create the CA key-pair as a root certificate, i.e. it will be “signed” by itself. It is trusted because we say so!

  2. Handle the key-pair for https

    1. Create the key-pair, private and public key

    2. Prepare the public key to be signed by creating the “Certificate signing request” (CSR) based on the public key

    3. Sign the public key with our CA private key

  3. Handle the key-pair for dovecot and postfix

    1. Create the key-pair, private and public key

    2. Prepare the public key to be signed by creating the “Certificate signing request” (CSR) based on the public key

    3. c. Sign the public key with our CA private key

Please read through the above steps again and make sure you understand the principle. (In practice the creation of the key-pair and the signing request is done in one step – but logically they are separate.)

Caution

There is no shortage of description on the net on how to create so called self-signed certificates. However many of them are dated and based on very old ways of doing things which have just been inherited out of laziness and without propre understanding of the tools involved.

For example, many descriptions do not add the “-nodes” flag as we do in these examples. This will force a password to be created for the private key in certificates and since this is usually not wanted (as described below) one extra step is then required to remove the password. Hence making the description unnecessarily complicated. Another example of obsoleted usage is the option “nsCertType = server” in config files. This option is since long superseded and is not even necessary in our context. Again, adding complexity where none is needed. Another (very popular) complexity adder is to create the private key separately from the certificate request with another obsoleted command; “openssl genrsa”.

Yet another plain wrong way that many HowTo:s show is to create the initial serial number for the certificates in the database (that “openssl ca” keeps of all signed certificates ) by simply storing a number one in a file (usually by “echo 01 > serial”). Instead the option “-create_serial” should be given to let openssl initialize a random 128 bit serial number.

Dealing with SSL/TLS certificate introduces many new terms and takes a while getting used to especially since “openssl” is not exactly easy to use. It has evolved (together with the standards) for a long time and old options that are since long superseded remains. However, there is no need to make things more black magic than necessary and the way we show below is what we believe the absolute easiest way to accomplish what we need in the minimum number of steps.

E.1 The use of the term “self-signed certificates”

The term self-signed certificate has two distinct meanings. It could mean that we sign a certificate that we have generated our self with our own CA (root) certificate that we have either created (most likely) or bought (highly unlikely). This is the way we use the term self-signed certificate in this appendix.

It could also mean that we create a CA-type certificate which is (almost) a regular certificate that it not signed by anyone but have a flag inside it that says “trust me, because I say so – I’m a root certificate”. This is really what openssl means by self-signing, the certificate is signed by itself.

Many of the tools out there create this latter type of certificate to avoid having to create a separate CA (root certificate)
