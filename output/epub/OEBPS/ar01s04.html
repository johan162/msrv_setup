4 Setting up Apache HTTP-server

To setup Apache we will first create and enable SSL/TLS certificates to be able to connect over https:// protocol to the server. After this we will define a separate document root for the HTTPS traffic and finally enable PHP5 for the secured version of Apache.

To separate the normal document root (that is accessed through http://) and the secure root (accessed through https://) we will also create a new secure document root at “/srv/www/ssl-htdoc”.

In the following we will assume that you have installed Apache v2.x together with the Apache PHP5 module through SuSE package management.

Caution

Please make sure that you can access a test page using normal HTTP traffic to your Web-server before continuing!

4.1 Creating self-signed SSL/TLS certificate for Apache

Creating SSL/TLS certificates for the https:// protocol is as mentioned above is straightforward but tedious. The good news here is that in OpenSuSE there is a shell script that does all the steps involved in creating certificates semi-automatically using openssl, “gensslcert”. The built-in help in this script will show all necessary options for the certificates. So running

$> gensslcert -h

will give you the list of all options. In the example command line below we will assume that the server resides in Sweden (country code SE) and accessed through the IP address 192.168.0.50 (in the address range reserved for a local net which is not directly connected to the internet). The IP address specified on the command line is rather important (it is the CN name) as described in the previous section on SSL/TLS. When your browser accesses the server it will check that the certificate it received from the server matches the URL used to access the server. If there is a mismatch the browser will generate a warning that the site should not be trusted (since the certificate could have been made out to another server and then just copied). This might cause some irritation since it is common for a home-server to be multi-homed, i.e. accessed via different paths or URLs. An example might be a dynamic DNS setup to access the home server from anywhere in the world with a domain name of choice, say “http://myserver.dyndns.com” . In addition a server can also be accessed in the local network, for example as http://192.168.0.50.

So there is a choice to be made here. The domain name which you most often use to connect to your server should be used in the certificate (as given in the Common Name field). This way you get the fewest warnings when connecting to your server.

Tip

With a more advanced setup for the certificate handling, described in Appendix E, it is possible to setup several “alias” addresses for the same server (using the AltN field in the certificate) to avoid this kind of irritating warning messages.

in our case we will use the IP as the common name for the server certificate so we call the utility script as:

$> gensslcert –y 3650 –Y 7000 –c SE –n 192.168.0.50

This will create both our own trusted root certificate as well as the certificate for the server itself and then sign the certificates with our own root certificate. Our self-signed certificate will be valid for 10 years (~3650 days) and valid for the server that is accessed by the IP address 192.168.0.50. Our CA (root) certificate will be valid for roughly 20 years (~7000 days). It is still possible to access the server through other URLSs for example by its name (if you have put it in your “/etc/hosts” file or even have a local DNS setup) but the browser will issue a warning in that case that it cannot validate the authenticity of the server. The exact wording of the warning (and appearance) is browser dependent.

After you have run this script the necessary certificate files will be stored under various subdirectories “/etc/apache2/ssl.*” as shown in Table 4.

After the certificates have been created we must now enable SSL and set the document root correctly in Apache for the virtual host which will handle the incoming HTTPS connections.

Table 4: Certificate/keys generated by "gensslcert"

Cert/key fileDescription
ssl.crt/192.168.0.50-server.crtX509 SSL/TLS certificate. The certificate contains the public key of the server.
ssl.key/192.168.0.50-server.keySSL/TLS private key. Must be kept private at all times!
ssl.crt/192.168.0.50-ca.crtThe CA root certificate (public key). This file should be imported to your Web-browser to avoid the “unrecognized certificate“ warning when you are connecting to your HTTPS connection.
ssl.key/192.168.0.50-ca.keyThe CA root private key. Should be kept private at all times!

4.2 Enabling SSL in the OpenSuSE configuration

Many of the configurations in the apache configuration script templates available with OpenSuSE have conditional statements whether SSL/TSL is enabled or not. This is controlled by a single flag stored in the configuration file “/etc/sysconfig/apache2”. In this file a number of variables define the setup for Apache. Here there are two variables that must be correctly set.

First the string variable APACHE_MODULES has to have “ssl” defined in the list of modules to be loaded. This module is added by Yast when Apache is installed. If this module is missing there is a risk that you have not properly installed Apache with the necessary mod_ssl module.

Secondly the SSL flag must be set as a Apache server flag as 

APACHE_SERVER_FLAGS=”SSL”

This must be set in order to enable the lines surrounded by a conditional “<IfDefine SSL>” statement in the various Apache configuration files.

Note

To avoid manually editing /etc/sysconfig/apache2 in oder to enable or disable Apache modules or flags there are two command line tools that can do this, "a2enflag" and "a2enmod". These two command are used to disable/enable flags and modules in syconfig file.

For example the following two commands would add both the SSL flag and the module mod_ssl to the configuration file

$> a2enflag SSL
$> a2enmod ssl

To list all the currently enabled modules use the following command (the modules listed below are just examples and does not necessary reflect what must be loaded.)

$> a2enmod -l
actions alias auth_basic authn_file authz_host authz_groupfile \ 
authz_default authz_user autoindex cgi dir env expires proxy \
proxy_http proxy_html include log_config mime negotiation \
setenvif ssl userdir rewrite php5 dav dav_svn

4.3 Setting up a virtual host for HTTPS

What we want to do now is to make use of the certificates we created and have Apache look in the alternative document root “/srv/www/ssl-htdocs” when the server receives a request over “https://”

Note

Strictly speaking there is no need to have a separate document root for HTTPS. It is possible to use the same document root as for normal HTTP traffic. However, for security reasons it is better to put pages that should only be accessible through the HTTPS in a separate root to avoid the risk that they are accessed through the normal HTTP protocol by mistake.

We will be very short in the description here since configuring Apache is not necessarily difficult but requires a lot of text to explain all the details. So in this context we will just show what is needed with a minimum of explanations (there are entire books written on Apache configurations to consult). In Appendix F. there is a also a complete configuration file as an example.

To setup the new document root for the https:// connection start with the following four steps:

  1. Switch to root user

  2. Create the enw document root for HTTPS://

    $> mkdir /srv/www/ssl-htdocs

  3. Change to directory /etc/apache2/vhosts.d

  4. Copy the template config file for an SSL-enabled server as a starting point

    $> cd /etc/apache2/vhost
$> cp vhost-ssl.template vhost-ssl.conf

We shall now edit the vhost-ssl.conf file so that Apache finds the certificates we want to use and the new document root we just created. Find the following variables in the configuration file we just copied (vhost-ssl.conf) and change them as shown below

# Setup document root and server name
DocumentRoot “/srv/www/ssl-htdocs”
ServerName 192.168.0.50:443  

# Setup log files
ErrorLog /var/log/apache2/ssl-error.log
TransferLog /var/log/apache2/ssl-access.log  

# Tell Apache where to find the certificate files  
SSLCertificateFile /etc/apache2/ssl.crt/192.168.0.50-server.crt
SSLCertifictaeKeyFile /etc/apache2/ssl.key/192.168.0.50-server.key
SSLCertifictaeChainFile /etc/apache2/ssl.crt/192.168.0.50-ca.crt

After you have changed this we need to tell Apache to accept the new document root. Add the following lines just after the TransferLog directive (as long as it appears within the “<VirtualHost _default_:443> … </VirtualHost>” it is really irrelevant where you put it)

<Directory “/srv/www/ssl-htdocs”>
  Options None
  AllowOverride All
  Order allow,deny
  Allow from all
</Directory>

To also enable PHP5 and any other configurations that is available for the standard Web-server we include all the other configurations files as well by adding the line below Just before the <Directory> directive (this assumes that you have installed mod_php5 for use with Apache previously)

Include /etc/apache2/conf.d/*.conf

Any additional configuration files added to your Apache setup (possible by Yast) will be read also for our encrypted setup in this way.

Please look at the (very) readable Apache documentation for a more detailed explanation of possible setups. It is also highly likely that in the end you may want to tailor the setup according to your own needs (most likely you want to change the Options parameter for the document root directory, for example to allow symbolic links to be followed).

Tip

In Appendix Fwe show an example of a complete vhost-ssl.conf file.

4.4 Restarting and enabling Apache

What remains now is to restart Apache and make sure there are no errors. To do this execute the following commands as root and verify that there are no errors. If there are any errors go back and check for spelling mistakes in the configuration files. Error messages to help pinpoint the problem can usually be found in "/var/log/messages" or in the directory "/var/log/apache2/"

$> rcapache2 restart
Syntax OK
Shutting down httpd2 (waiting for children to terminate)    done
Starting httpd2 (prefork)                                   done

Tip

If you are used to SysV ini files you could as well start the server with the line 

$> /etc/init.d/apache2 restart

/sbin/rcapache2 is just a symbolic link to the corresponding init.d script

After this you probably also want to have Apache start automatically each time you start your server. If you haven’t already done so give the command (as root):

$> chkconfig –add apache2

This will add Apache daemon as a service in the default run levels for your machine. This could also be done by opening Yast and go into <system->runlevels> and add Apache as a service to be started.

Before continue verify that you can make a connection to Apache over HTTPS (for example by just creating a single line “index.html” in the root directory and just call https://localhost/index.html from the browser)

Be aware that there will be a warning about this being an untrusted site since the root certificate we use have not been installed in the browser as a trusted certificate. For now just ignore this.
