6 Setting up postfix

To remind ourself where we are in the overall setup process the setup of postfix will make it possible to send mails from our own machine by connecting to a running postfix daemon via the SMTP(S) protocol.

All relevant postfix configuration files can be found in the /etc/postfix/ directory. In the first instance we will setup postfix using a regular SMTP connection without the added complexity of a SSL/TLS certificate. Once we have this working we will modify the configuration to use the same key and certificate we created for Dovecot. This will work just fine as long as Dovecot and the SMTP server are running on the same host. If they are running on separate hosts a separate and unique certificate for postfix must be created since each server with unique IP address must have its own certificate (to avoid warnings from clients connecting to them).

In postfix there are two files in the /etc/postfix directory. we need to update:

  • main.cf - This is where all settings are stored, one huge parameter file

  • master.cf - This file controls what helper processes are started and on what ports they are listening.

Caution

The changes you make manually in the postfix configuration might come into conflict if you later on decide to use Yast setup for the mail server. So don’t use the YAST setup once you have manually configured postfix (into perfection!). Actually we would recommend against using Yast mail server setup for any serious mail server since the tuning possibilities are near to zero.

Also, please be careful when editing the configuration file and watch out for setting the correct server variable. Sender or receiver, i.e. with prefix smtp_<variable> or smtpd_<variable> this is a common source of errors that can be surprisingly time consuming to find.

6.1 User authentication in postfix

Before we continue we need to discuss how postfix handles user authentication. When do we need that? By default postfix restricts who can use our server to send mail based on IP address. It will allow clients on the same sub-network as the server. However, with mobile usage we will most likely connect to our postfix server through a broadband router and then the router will forward our request to the server. Hence the request looks like it is coming from our sub-network (our gateway) and will be allowed. This would then allow anyone that knows our official IP address to the gateway (and the port to use) to use our SMTP server to send mail that looks like it is coming from us! This is what is known as an open relay and is something really bad.

So, we need a way to authenticate users before they are allowed to send mail via the SMTP server. By itself postfix has no built-in method for this. Instead it is constructed to use an external library which implements an API known as SASL (Simple Authentications and Security Layer). The SASL library is a completely independent of postfix. There are several available providers of a compliant SASL library (for example the SASL authentication daemon saslauthd). The good news here is that Dovecot provides one possible implementation of a SASL library. Since we already have Dovecot installed it seems a good idea to use it. As you may recall we made some provisions for this when we configured Dovecot (even though we didn't explain the details at the time).

So after we have configured postfix to use the Dovecot SASL the following happens when a user connects.

  1. Postfix send the authentication details through the SASL API to Dovecot

  2. Dovecot receives the authentication details and uses the configured way to lookup the user details. By default dovecot uses the Linux PAM framework which normally is configured to check the user and password from the shadow password file. This requires all mail users to also have an account on the server. Dovecot can also use other methods such as an LDAP server or even a database with all the user credentials stored. The main advantage with storing users in a DB is that they do not need to have user accounts on the server.

  3. Dovecot returns fail or success to postfix which based on this knows whether to accept or reject the incoming call.

There is still one problem with this authentication setup in that the user and passwords are sent in plain text over the network. For automatic network sniffers this is a gold mine since harvesting valid user/passwords combos is what spammers are after. The way to protect our conversation is to use SSL/TLS encryption of the communication between the client and the server in the same way we protected the IMAP and https:// traffic.

Note

SSL (Secure Socket Layer) was renamed TLS (Transport Layer Security) by the IETF (Internet Engineering Task Force) as of version 3.1. There are some technical differences between SSL and TLS but for all practical reasons (as far as we are concerned) they are the same.

6.1.1 Configuring Dovecot SASL in postfix

Assuming we keep the network settings as default (allowing clients from the same sub-network to connect). We need to add/change the following settings in the postfix configuration file.

smtpd_sasl_auth_enable = yes
broken_sasl_auth_clients = yes
smtpd_sasl_type = dovecot
smtpd_sasl_path = private/auth
smtpd_sasl_security_options = noanonymous

Then add permit_sasl_authenticated to the smtpd_recipient_restrictions section as the following example shows 

smtpd_recipient_restrictions = permit_mynetworks, permit_sasl_authenticated, \
reject_unauth_destination

The order of these restrictions are important as it is to finish with reject_unauth_destination since by default the connection will just “fall through” and be allowed !

6.1.2 Configuring postfix to use our ISPs SMTP server

If your server, like most home servers, does not have a fixed IP address you cannot send mails directly from your home server since all official mail servers on the internet must have a fixed IP address and have a so called, MX record in the DNS server which identifies the server as a Mail eXchange server. Hence we must go through another proper mail server to send mail. This other mail server is usually our ISPs server (but it doesn’t have to be). This is known as making our SMTP server a relay server (since it relays mail to this other proper mail server).

Most likely we also need to give a username/password in order for us to be able to login to our ISPs mail server. In the following we assume that our ISP:s mail server is called “smtp.ourisp.com” and accepts connection not on the standard port 25 but on port 26 (just to show how to handle other ports)

We must then add the following line in the configuration file

relayhost = [smtp.ourisp.com]:26

(The reason for putting the provider address in brackets is to avoid an MX lookup which can provide some problems. There are some valid (and good) reasons for this. But again, it would take too far outside this document to fully explain this.)

We also need to provide the correct user/password that our ISP has given us. In main.cf we point to a file where these credentials are stored.

smtp_sasl_password_maps = hash:/etc/postfix/sasl_passwd

and in the file sasl_passwd we add the line 

[smtp.ourisp.com]:26 username:password

where the username:password are replaced by the proper values. Note that since both the username and password is in plain text this file should only be readable by root.

In order to update the corresponding sasl_password.db file run

$> postmap sasl_password

Finally we also need to restart (or reload) the postfix server

$> rcpostfix restart

Note

Postfix hash files.

As you can see above the filename is prepended with a “hash:” prefix. This tells postfix not to use the file directly but a database version of the file. This is done for efficiency reason and if you look in the main.cf file you will indeed see that all text files are accessed as hash files. This has one complication. If you update the source text file the database file also have to be updated. To update the sasl_passwd.db database file from the source sasl_passwd the utility toll 'postmap' is used:

Change into /etc/postfix directory and run

$> postmap sasl_passwd

This will create the sasl_passwd.db file that is used by postfix.

6.1.3 Verifying postfix SASL connection

Before moving on we should make sure that this works as we have intended. We can do this in the same way as we tested the IMAP connection, by hand. This allows us to see the core protocol level without any client getting in our way.

Unfortunately the SMTP protocol doesn't send the user/password combo as plain text as we did in the IMAP protocol testing. Instead SMTP expects the user/password to be base64 encoded together in one string. This can be manually constructed with the use of a one line perl script as shown below

$> perl -MMIME::Base64 -e 'print encode_base64("\000user\000userpasswd");'
AHVzZXIAdXNlcnBhc3N3ZA==

Note

Strictly speaking (following the protocol) the username should be repeated so the really correct string would be 

encode_base64("user\000user\000userpasswd")

but the simplified version will work. Another variant to do the base64 encoding is to use the Unix command ‘mmencode’ which does Base64 encoding. This could be used as in 

$> printf ‘\000user\000userpasswd’| mmencode

This is actually simpler then the Perl version but might not be available on all systems. ‘mmencode’ can also be used to decode base64 encoded text.

where you replace the <user> and <userpasswd> placeholders as needed. It is then possible to use the result above when using telnet to login to the SMTP server and giving the AUTH PLAIN command.

$> telnet localhost 25
telnet localhost 25
Trying ::1...
Connected to localhost.
Escape character is '^]'.
220 myserver.com ESMTP Postfix
EHLO myserver.com
250-myserver.com
250-PIPELINING
250-SIZE
250-VRFY
250-ETRN
250-AUTH PLAIN
250-AUTH=PLAIN
250-ENHANCEDSTATUSCODES
250-8BITMIME
250 DSN
AUTH PLAIN AHVzZXIAdXNlcnBhc3N3ZA==
235 2.7.0 Authentication successful
quit
221 2.0.0 Bye
Connection closed by foreign host.

To make things clear the lines in bold face are the lines we entered. The rest of the lines are the replies from the SMTP server.

Make sure that you can see the line 250-AUTH PLAIN since this is the line that indicates that the server accept authentication.

6.1.4 making an alias for root

We also want to have any system mail for root delivered to a “real” user. For this we need to setup an alias for root. This is done by making sure that the file /etc/aliases has a line 

root: <user>

where <user> is a real existing user that will receive the root mails. After you have updated this file you need to run the command “newaliases” which will produce the file alias.db based on the original alias file.

6.1.5 Rewriting sender addresses

If a mail is sent from the local user on a server that is not directly connected to the internet it will have a domain name that in most cases are “fake”, for example <joe@localhost.nil> (this will of course depend on what name you have given the server). The problem with this is twofold. First the recipient cannot answer to this address and secondly most mail servers requires that the from-address is a valid (can be looked up in DNS) to forward the mail at all.

To correct this situation postfix has the ability to rewrite your “bad” addresses to something the recipient can actually answer to. In fact, a lot of the complexity in postfix comes from the various ways of rewriting addresses. Here we will just use the most basic rewrite functionality. For a fuller (and very readable) discussion on the rewrite options in postfix consult the postfix HowTo “Postfix Address Rewriting” available on the postfix website.

This type of address rewriting is also known as address “masquerading” (for obvious reasons).

In order to have postfix translate the “bad” mail address to a “good” address a file with mappings between “bad” and “good” must be created. In this case we will use a map/file called “sender_canonical”. For example, assuming that “joe” want all his sent mail to look like it is coming from his GMail account <joe@gmail.com> we then add the following line to the sender_canonical file

joe     joe@gmail.com

After this we need to run the postmap (to create the DB file) and tell postfix to reload the configuration to make use of this new masquerading as

$> postmap sender_canonical
$> postfix reload

6.2 Setting up SSL/TLS for postfix

6.2.1 Installing certificates

As mentioned above we can use the same certificates we created for dovecot as long as postfix is running on the same server as Dovecot (same IP address).

The certificate and key we created for Dovecot were shown in Table 6. We must now tell postfix to enable SSL/TLS for incoming connections as well as point postfix to those certificates that we want to use.

To do this we update main.cf as shown below

smtpd_tls_security_level = may
smtpd_tls_key_file = /etc/ssl/private/dovecot.pem
smtpd_tls_cert_file = /etc/ssl/certs/dovecot.pem
smtpd_tls_loglevel = 1
tls_random_source = dev:/dev/urandom
smtpd_tls_auth_only = yes

Note

The above line

smtpd_tls_security_level = may

replaces the older

smtpd_use_tls = yes

and tells postfix to use TLS.

For debugging purposes the loglevel can be increased to ‘2’.

The final setting, smtpd_tls_auth_only = yes, forces the use of TLS for SASL authentication and will not allow plain text authentication to occur unless a SSL/TLS session has been established. (It may therefore be useful to comment out smtpd_tls_auth_only = yes during testing.)

6.2.2 Accessing an encrypted server

Historically a separate port have been used for the encrypted version of the SMTP protocol when SSL was used. With SSL (and not TLS!) this is needed since the entire conversation is encrypted so the server listening on the port has to use encryption from the start. The only real user noticeable difference between SSL and TLS is that with the modern TLS it is possible to start the conversation non-encrypted and as soon as both client and server has agreed to use encryption the rest of the conversation is encrypted. One of the big advantages with TLS is therefore that it is possible to use the same port for both encrypted and non-encrypted traffic (as defined by RFC 3207) .

This means that we now have a choice on how we setup the actual access to the server over the encrypted connections.

  • Use a dedicated port (old way) with SSL or

  • Use the same port with TLS

For all modern installation it is strongly recommended to use the modern way with the same port using TLS.

6.2.3 Using a dedicated port for encrypted traffic

Again, this is NOT the recommended way but is included for completion. Unless you know that some clients only support this way you should not implement this.

Originally port 465 was used as the separate SSL port for encrypted SMTP or SMTPS (sometimes also referred to as SSMTP). Unfortunately this port assignment was never made official as far as IANA recognized port numbers go. Instead it is registered for URD – “URL Rendesvous Directory for SSM” by Cisco.

In addition the original intention of port 465 was to let SMTP servers forward mail between each other over an encrypted channel. It was never intended to be used by mail clients to talk to the server directly. For this purpose another port was to be used, port 587 “Message submission” (see RFC 2476).

So using this older setup an SMTP server was really supposed to be listening on three ports. Port 25 for normal unencrypted traffic both from other servers and from clients, port 465 to allow other servers to communicate and finally port 587 to allow mail clients to submit new mails.

However, reality doesn't necessarily always match the theory. Most servers only use two port, one for unencrypted and one for encrypted traffic. Even though technically incorrect most servers use port 465 for SMTPS (both from clients and other severs).

For a home based server (which does not have a DNS entry as a registered MX server connected directly to the internet as an official mail server) it doesn't really matter if you choose the common (but incorrect) port 465 or port 587 as long as you configure your clients correctly on which port they should use to send mails. The only thing you need to watch out for when using port 465 is that since this is not an officially assigned port for SMTPS one extra step is needed as described below.

Using port 465 for encrypted SMTP traffic

Since port 465 is not an officially recognized port for SMTPS we must either update /etc/services (that is a file which lists all officially recognized ports and gives symbolic names to them) to be able to use the symbolic name “smtps” for the port in our master.cnf postfix or use the port number directly.

To use the symbolic name we must add the line 

smtps   465/tcp

to /etc/services and remove any other service registered to that port. The entry in /etc/services is only made to be able to refer to the port number with a symbolic name.

The next step is to instruct postfix to listen on this port and enable the manger process that handles the TLS connections for postfix. This is done by editing master.cf and first removing the comment for the following line:

smtps    inet  n    -    n    -    -    SMTPD –o smtpd_tls_wrappermode=yes

and then removing the comment for the line

tlsmgr    unix    -    -    n    1000?    1 \  tlsmgr

For these new settings to take place we now need to restart postfix

$> rcpostfix restart

Tip

As alternative you could skip the editing of /etc/services and just enter the numeric port number directly in master.cnf but this is a more “hackery” way of administer a server. It’s best to have all the services recognized on the server listed in /etc/services.

Using port 587 for encrypted SMTP traffic

Since port 587 is an officially recognized port there is no need to update /etc/services . The only update needed is to remove the comments in master.cnf for the two lines

tlsmgr    unix    -    -    n    1000?    1   tlsmgr

and

submission inet n       -       n       -       -       smtpd

This will enable the server to listen on port 587.

If you look in the master.cnf file you will also see that by default some optional parameters are give directly on the command line. The parameters are mirrors of the ones given in the main.cnf but will take precedence. The command line parameters are useful when you need different set of parameters for different ports.

Actually port 587 should really be used for submitting emails even if no encryption is used. Unfortunately many commercial providers do not follow this recognized standard and just assumes that both clients and other servers would contact them on port 25.

If you want to use port 587 for submission with only optional encryption for those client requesting this just remove the “smtpd_tls_auth_only = yes” option and SSL/TLS encryption will be optional.

6.2.4 Using the same port for both encrypted and non-encrypted traffic

This is the recommended way for a modern secure SMTP server setup.

With this method no extra ports are needed. Instead the normal port 25 is used for both encrypted and non encrypted traffic. When a client first connects to the server it will notice the by the servers response that TLS is supported (by the STARTTLS response code) and if the client is also capable of TLS encryption it might then ask the server to continue the rest of the conversation using SSL/TLS encryption.

To enable this method it suffices to enable the tlsmgr by uncommenting the line

tlsmgr    unix  -       -       n       1000?   1       tlsmgr

in master.cnf

This might seem contradictory to what we recommended in the previous paragraph regarding the use of port 587. Technically you would be correct. The advantage is that some poorly written clients will only support port 25. In addition keeping as few ports open as possible is a good thing from a security point.

This is simply case where there simply is no single one correct answer. The official standard stipulates one thing but years of de-facto standard shows something else. Most (all?) ISP do not even allow incoming traffic on port 587 (which they really should!) and many clients only support port 25 for unencrypted submission and port 465 for encrypted submission (which technically is the wrong way of doing it).

6.2.5 Verifying the SSL/TLS setup when using a different SSL port

Finally we need to verify our setup. To verify that SSL/TLS is enabled in postfix we start by open a plain telnet session to postfix on the normal (non-secure) port 25

$> telnet localhost 25
telnet localhost 25
Trying ::1...
Connected to localhost.
Escape character is '^]'.
220 myserver.com ESMTP Postfix
EHLO myserver.com
250-myserver.com
250-PIPELINING
250-SIZE
250-VRFY
250-ETRN
250-STARTTLS
250-ENHANCEDSTATUSCODES
250-8BITMIME
250 DSN
quit
221 2.0.0 Bye
Connection closed by foreign host.

The thing to notice above is the absence of AUTH PLAIN (since we disabled that unless we had a secure connection which we don’t have since we connected with telnet) and the addition of 250-STARTTLS which indicates that postfix is ready to accept a secure connection over TLS

The rest of the section assumes that the server has been setup to listen on port 465 for secure connections.

The next step therefore is to verify the encrypted connection in the same way as we did for the IMAP server using the “openssl s_client” command (see s_client(1) for more details).

$> openssl s_client –connect localhost:465

This will first give you a long list of SSL/TLS details and in the end you will see a line like

220 smtp.myserver.com ESMTP Postfix

You can then give the EHLO myserver.com command to see what capabilities are supported and it should be the same as in the previous telnet session but without the STARTTLS info line since we are already in a TLS session but with the AUTH PLAIN (and AUTH=PLAIN) indicating that postfix is ready to accept an incoming login. After this you should also try to login in the same way we did without SSL/TLS (just remember the base64 encoding).

Once this is working you should try to access the SMTP server using the full IP address or hostname, for example as

$> openssl s_client –connect 192.168.0.50:465

It is possible that this will fail. In that case it most certainly is caused by you having the following line

inet_interfaces = localhost

In main.cf . This line tells postfix to only accept incoming connection only to localhost and not the IP address. Recall that the network card can be accessed with (at least) two IP addresses first the loopback address 127.0.0.1 (or localhost) and then the assigned IP address (in our case 192.168.0.50). Either remove the line completely or add the IP address of the host to the line, i.e. in this case. As a general rule you should try to clean up your postfix configuration file to only contain settings you have made yourself and then comment them heavily, (the shorter the configuration file is the easier it is to understand).

To fix this you could remove the line or add the IP address of the server as

inet_interfaces = localhost, 192.168.50

(Leaving inet_interfaces empty or setting it to “all” will accept connection on all defined interfaces on this machine.) With the above use of openssl s_client you will get a certificate warning that openssl can not verify the root certificate. This is to be expected since we have not told openssl what root certificate we trust. In our case this warning is harmless but to avoid this warning add the parameter -CAfile </path/to/rootcert/ca.crt>

If you have followed the previous recommended Apache setup then one place to find our root certificate is 

$> openssl s_client -CAfile /etc/apache2/ssl.crt/ca.crt –connect 192.168.0.50:465

6.2.6 Verifying the SSL/TLS setup when using one port for both encrypted and non-encrypted traffic

This also requires the use of the openssl with the s_client command.

However since the connection starts out non-encrypted and must be enabled by following the SMTP protocol we must add an extra option -starttls smtp to tell openssl to obey the SMTP protocol as 

$> openssl s_client -starttls smtp -connect 192.168.0.50:25

The rest of the tests can be done in the same way as in the previous section.

Tip

For more complex testing of SMTP transaction we recommend the program “swaks” which stands for Swiss Army Knife SMTP. This is a scriptable tool which simplifies complex SMTP testing SMTP including SSL/TLS. See http://www.jetmore.org/john/code/swaks/

6.3 Enabling postfix at boot time

Finally to have postfix start automatically when the server is started we use the 'chkconfig' command

$> chkconfig –add postfix
