2 Overview of the components

Unfortunately there isn't one simple program that will do all what we need. Instead we will need a number of components to achieve our goal. A server setup with IMAP/SMTP has some reputation of being “black-magic” to setup. However, this is mostly based on the fact that there are many different parts involved and misunderstanding the role of (or interactions between) the different actors will definitely make the process seem like black magic. So lets start by discussing the parts involved and give a high level logical overview on how the parts interact. For a pictorial overview please refer to Figure 2

2.1 Postfix

This is the SMTP/SMTPD server/daemon that handles the mail protocols we will be using. The Postfix server is abstractly known as an MTA (Mail Transfer Agent) in mail lingo. These are the backbones of message transfer over the internet. The role of the MTAs are to receive and forward messages to other MTAs depending on the end address. This forwarding continues until the message reaches the server that is responsible for the domain the message is addressed to. Once the message is at its final destination it gets delivered to the appropriate user in that domain.

The headers in a typical message will show which MTAs have been passed in the process of delivering the mail from the sender to the recipient.

Initially a user creates a message with some mail client, a mail client is abstractly known as MUA, Mail User Agent) examples are (for example) KMail, Thunderbird or Roundcube. The MUA initially connects to a specified MTA that receives the message. The MTA examines the headers in the mail and determines if it should forward the message to some other MTA or if the message is to be locally delivered.

The reason for using this abstract language instead of referring to the specific programs we are using is to be able to discuss mails without referring to specific protocols or applications.

All of the above is relevant only to officially registered mail servers for a specific domain. These mail serves are recognized in the DNS system with a so called MX record (Mail eXchange). A home based server is normally not an officially recognized mail server fresponsible for a particular domain. Instead the home MTA has to be configured to relay messages it receives from a mail client on to an official mail server. This is normally the mail server at the ISP.

Note

For a proper email server connected to the internet with a MX (Mail eXchange) record in its DNS entry there are many more details to take into account. For example DKIM, FBL and SPF just to name a few techniques and methods a sysadmin has to be familiar with. Luckily for a home server we can ignore this.

Postfix has two separate and distinct roles, one as a sending server, an SMTP server, and one as a receiving daemon, the SMTPD server. The SMTP server is responsible for sending mail to other servers while the receiving server is a daemon that waits for connections from other servers (or clients) to receive messages. Any messages that should be delivered locally will be stored the users mailbox and any message with a recipient outside the domain the server is responsible for will be forwarded to the next mail server depending on the end address.

By default the assigned port that the receiving MTA server listens on for non-encrypted messages are on port 25, see figure Figure 3. This is the port that is used both when other MTAs to talk to our server to forward messages as well as the port that mail clients connects on to initially send messages created by the client. (This is how most setups work in practice for historical reasons. However, this is not really in compliance with the original RFCs. In the original specifications port 25 should only be used for MTA to MTA communication and port 587 should be used when a mail clients want to send a new message to a MTA.)

An important part of this setup is that the server will relay all incoming mails to the ISPs mail server which will then send it to the rest of the world. Most ISP will not allow neither outgoing nor incoming traffic on port 25 to any other servers besides their own. This makes it impossible to either directly send messages on port 25 to our server from the ouside or to use any other mail server besides the ISP to forward our messages to. The ISPs block port 25 in an futile attempt to block spams that are sent by Trojan mail servers running on unsuspecting servers. The reason this is futile is that it is as easy to use another port on the server for the spammers. The ISP who is blocking of port 25 is today mainly just an irritation for advanced users. It does not stop spam in any shape or form.

What we need to do in order to send mail via our home server is to use another port, connect to that other port and have postfix relay our message to be sent to our ISPs official mail server. This will of course assume that we have told our SMTPD daemon to listen on that port.

The reasons we do not have our mail clients connect directly to our ISPs mail server but instead going through our home server are twofold:

  • most ISP does not allow connections to their mail server unless the connections originate from somewhere within their own network. That means it would be impossible to directly connect to the ISP mail server from some device outside the subnet controlled by the ISP, say a smartphone.

  • the second reason is that we want to be able to send local mails originating in our server (for example system mail) to a valid address (this will also require us to alias a local user to a real email address since most mail servers refuses to pass on messages with a bogus sender address, say "<root@localhost>")

2.2 Dovecot

All messages needs to be stored in a structured way on disk for each user. The two formats mostly used in the Unix/Linux world are.

  • "maildir" format. This format stores all messages as individual files in a directory structure corresponding to the mail folders defined.

  • "mbox" format. This format stores all messages lumped together in one file. Historically this is the "original" message storing format. For all practical purposes this should not be usedin new setups.

For all modern installation it is strongly recommended to use the "maildir" format. This is the format we will setup Dovecot to use in Section 5 .

In order to access the mail storage the most flexible way is through an IMAP server (the old and mainly obsolete way being through a POP3 server). It is important to understand that an IMAP server is only responsible to manipulate messages (files) on disk storage. The IMAP server is like mother goose watching over the mail storage. It is not involved in neither sending nor receiving messages in any shape or form. The mail user agent (MUA) connects to the IMAP server and reads the messages for its user. Messages are always kept at the server even after they have been read. This will allow us to later synchronize the message storage with any other devices and messages that are marked as read on one device will show up read on all other devices as soon as they synchronize their mails. For efficiency reason most mail clients choses to cache messages locally in order not to have to transfer them from the server each time the user decides to open the message. In our case we will later on show how to setup a web based mailer and in that case there will be no local caching and messages are only stored on the server.

For now we can also assume that it is the responsibility of some other program to actually store the incoming messages in the mail storage (on disk). In mail lingo such a program that stores messages locally on disk is called LDA (Local Delivery Agent).

The main responsibility for an IMAP server is to allow authenticated users to access their messages and update the status of messages such as read or moved to a different mail folder.

So how can Dovecot keep track of mails if any other program can write new mails into the storage?

On Linux Dovecot uses notifications of file changes to get information on when new mails arrive (using the inotify mechanism). By subscribing to file changes in the mail directories it is possible for dovecot to maintain information and indexes (to quickly find mail). There is also a structure in the maildir directories on where to store new mails so Dovecot knows exactly where to look for new messages.

One reason for choosing Dovecot as our IMAP server (there are others as well) is the fact that it is fast, extremely robust and it is almost impossible to get into a corrupt IMAP state. Even removing all the index files will have no effect. Dovecot will just notice that the files are gone and recreate them by re-reading mails in the storage as necessary.

Dovecot is also the only widely available IMAP server (including some well-known commercially available servers) that fully passes the complete IMAP stress test (see http://www.imapwiki.org/ImapTest/ServerStatus)

Note

Dovecot is to large extent the creation of a single individual, a finish software engineer with the name of Timo Sirainen.

More information on Dovecot can be found at http://dovecot.org/

2.3 Fetchmail

Since external MTA servers can not connect to us directly in order to periodically push new messages to us we must have some method to gather messages from external mail accounts and store them in our mail repository. This is the only way we can receive messages assuming we are configuring a home server which lacks the ability to act as an official domain mail server. Enter here the aptly named program fetchmail.

This program is used to periodically authenticate and fetch new messages from external mail accounts and deliver them locally. We can, for example, setup fetchmail to gather messages from a GMail or Hotmail account so that they can later be accessed by the IMAP server.

The way fetchmail works is that it collects messages from external accounts and then delivers them to our MTA (postfix) on port 25. In effect making it look to postfix like it has received a mail from another MTA, see Figure 4.

Caution

Since fetchmail does not handle authentication at delivery on port 25 postfix must be setup to accept delivery from other daemons that run on the same server without requiring authentication. We will later show how to do that in the postfix setup section.

2.4 Procmail

The final bit of the puzzle, which strictly speaking is not necessary, will make things like spam filtering and rule based processing of messages possible. Procmail fills the role of a LDA (Local Delivery Agent), the last stage that receives a mail (from postfix) as input before storing it on the file system mail storage.

Procmail configuration is based on rules which uses pattern matching of messages together with a corresponding action to be taken when the pattern matches.

Depending on the user specified rules different actions can be taken depending on the content of the message. A common rule is to store incoming messages in a specific folder based on some criteria. This could for example be used to store identified spams in a specific folder, newsletters in another and the rest of the incoming messages in the inbox. The action in the rules are not just limited to sorting mails in different folders, external programs can also be called when a pattern matches.

The rules that control procmail on how to handle incoming mails are very flexible and it is easy to do things like passing certain mails to some programs for further processing or make automatic replies based on the content in the mail.

Unfortunately the syntax for specifying rules in procmail is an acquired taste at best and takes some getting used to. To ease the writing pain we have collected a few common and useful procmail recipes in Appendix B. On the net there are also dedicated pages with recipies for several commonly used procmail rules.

2.5 Roundcube (and Apache)

The above four actors (postfix, dovecot, fetchmail and procmail) are only one possible set of applications that can be used to create a basic mail server. Hower this particular combination can probably be considered one of the standards that both individuals larger organizations use.

In our setup we will also install a Web based mail client that will allow reading and manipulate of messages using any available Web browser.

The mail client will be installed in the same server and talk directly to our IMAP server, i.e. Dovecot. In our setup we will configure Apache (which is our web-server) to allow https:// protocol access to Roundcube.

We have chosen Roundcube since in our opinion it is one of the best free Ajax-based web-mail clients available and is easy to install. A screen shot from Roundcube is shown in Figure 6

2.6 openssl

This is a supporting library used by several other components. The openssl library is the de-facto standard encryption library on Linux based systems. It is used to both manipulate and create encryption keys as well as being library for other programs needing to encrypt data. The term openssl can refer both to the specific command openssl as well as to the overall library, the context will determine the suitable interpretation.

This library will among other things be used to setup a secure connection to our Webmail based on the HTTP protocol. We should already now say that the management of SSL (Secure Socket Layer) connections and the encryption/decryption keys via this library and its tools is somewhat convoluted. A large part of the confusion (as witnessed by the countless requests for help on the net) with this library is that very few takes the time to understand it. As a result many of the "recepies" found on the net is obsolete, misuses standards or are plain wrong. Unfortunate the developers of openssl and its tools have been kind enough to maintain compatibility with very old ways of doing things. This results in that old recepies that uses very antiquated ways still (kind of) work. Since most people (even administrators) are more than happy to just use something that seems to work (without understanding it) this has reulted in both some very bad habits when useing openssl as well as potential security weaknesses and inconviniences which could be easily avoided.

To remedy this situation we will explain in detailes and show the modern and secure way of setting up the necessary encryption/decryption infrastructure. To really cover all the details in an accessible way we have also added an entire appendix describing how to use the library Appendix E.

2.7 spamassassin

To help identify spam mails (i.e. unwanted junk mail) we will setup and use a Perl library called spamassassin. When a message is about to be delivered to the local user it will first be run through spamassassin. This program will then examine the message based on a number of both pre-defined and heuristic tests and give the mail a score to determine the likelihood that the message is junk. The calculated score is added as an additional header in the message.

After the score has been determined it is entirely up to the user that received the message to use the calculated score for further actions. The most common example is to have all messages above a certain score to be stored in the junk mail folder and those with a really high score to be deleted right away. We will later on show how to add procmail rules to handle this.
